## 二、问题详述

### 问题 1（主因）：`resetToNew()` 漏重置 `params`

```ts
// web/src/app/backtests/page.tsx:177
function resetToNew() {
  setSelectedId(null);
  setName('');
  setDescription('');
  setCode(DQ_TEMPLATE);   // code 重置了
  setLoadedConfig({});
  setBase(null);
  setErrors([]);
  setNotice('');
  // ← 缺 setParams(PARAMS_DEFAULT)
}
```

`params`（开始日期 / 结束日期 / 因子公式）**从未被重置**。

**实测证据**（真实浏览器驱动）：

```
=== 1. 用非默认参数保存：开始 2023-01-03 / 结束 2023-06-30 / 因子 pct_change_5 ===
=== 2. 切走（新建）再载入该策略 ===
  新建后 开始日期 = 2023-01-03      ← 期望 2024-01-01（默认）
  新建后 因子公式 = pct_change_5    ← 期望 pct_change_20（默认）
```

用户心智模型：「我点新建，应该得到一张白纸」。
实际行为：策略名清空了、代码回到模板了，**但回测区间/因子还停在上一个策略**。
于是「新建策略 → 直接编译运行」会拿着上一个策略的区间与因子去跑，
结果与预期不符 → 用户判断为「新建策略不行」。

#### 为什么表现为「按钮完全没反应」

实测点击前后的全部可见字段：

```
编辑中:  name=OLD_STRATEGY  描述=旧描述  开始=2019-09-09  因子=pct_change_5  codeLen=920

=== 点击顶部「新建」 ===
点后:    name=""           描述=""      开始=2019-09-09  因子=pct_change_5  codeLen=920
```

名称/描述确实被清空了，但**视觉重心的日期、因子、代码区纹丝不动**
（代码本来就处于模板态，重置还是同一个模板）。

更关键的是**第二次点击零变化**：

```
点前: {"name":"","start":"2019-09-09","formulas":"pct_change_5",...}
点后: {"name":"","start":"2019-09-09","formulas":"pct_change_5",...}
完全无变化 => 是
```

已处于新建态时，`resetToNew()` 把每个 state 都设成**它已经是的值**，
React 对相同值 bail out 不重渲染，DOM 一个像素都不动 —— 用户看到的就是「按钮是死的」。

**修复**：`resetToNew()` 补 `setParams({ ...PARAMS_DEFAULT })` 与 `setRunId(null)`。
同时 `handleSave` 把 `start`/`end` 一并写入 config，
`loadStrategy` 从中还原，保证「保存 → 重新载入」参数往返一致。

### 问题 2：`loadStrategy` 的 dirty 基准取错来源

```ts
// web/src/app/backtests/page.tsx:144
setBase({
  name: s?.name ?? '',
  description: s?.description ?? '',
  code: s?.source || '',
  params: { start: params.start, end: params.end, formulas },  // ← start/end 来自「当前编辑器」
});
```

注释自己都写明了正确意图（「dirty 基准的 params 必须来自策略自身的 config」），
但 `start`/`end` 仍然取的是组件当前闭包里的旧 `params`，只有 `formulas` 真正来自策略 config。

后果：从一个「日期为 A」的策略切到「日期为 B」的策略时，
`base.params.start = A`（旧值）而 `cur.params.start = B`（新载入值）→ 立刻误报「●未保存」。
反之也可能把真实的改动判成「未修改」。

**修复**：策略 config 里持久化 `start`/`end`（此前只存了 `factor_formulas`），
载入时一并回填，`base` 完全由策略自身数据构建。已随本次提交落地。

### 问题 3：同名保存 = 静默新建版本

后端 `save_strategy` 语义是「同名保存 → version + 1」（版本化设计，本身合理），
但前端在**已有同名策略**时再用同名新建，会静默产生 v2，
左栏按 `is_latest` 只显示一条，用户看到的是「列表没变化 / 我的新策略没了」。

实测：
```
POST {"name":"dup_check_x",...} → version: 1
POST {"name":"dup_check_x",...} → version: 2     ← 静默覆盖为最新
```

**修复建议**：前端在 `handleSave` 新建分支前查重，命中则提示
「已存在同名策略，继续将创建一个新版本（v{n+1}）」并要求确认；
或明示「另存为」与「更新当前」两条路径。

以下均已实测验证正常，**不要误改**：

- 「编译运行 ▶」全链路 —— 提交 → 轮询 → 出结果，实测 **38.7s** 完成（后端 ~26s 起）
- 参数持久化往返 —— 保存后用非默认参数重新载入，日期/因子均正确恢复
- 现有单测 —— 新 worktree 内 `11 files / 46 tests` 全绿

### 关于「编译运行」的体验问题（非缺陷，但值得优化）

回测平均耗时 26~39s，期间按钮显示「运行中…」、顶部提示「回测运行中…（执行中）」，
**没有进度条、没有已用时、没有取消按钮**，轮询间隔固定 2s，
10 分钟才超时。用户容易误判为「卡死了」，进而以为整个页面坏了。

建议：
- 显示已用时长（如「运行中… 12s」）
- 提供「取消」按钮（后端 job 已有状态机，可加取消端点）
- 轮询退避（2s → 3s → 5s），减少无谓请求

## 七、P0 完善（第二轮）

### 7.1 运行中反馈：阶段 + 已用时长 + 退避轮询

**问题**：回测实测 26~39s，前端只有一句「执行中…」，没有阶段、没有已用时长。
用户无法区分"在正常跑"和"卡死了"。

**根因**：后端的进度基建其实**早就存在** —— `enqueue()` 会按函数签名自动注入
`progress` 回调（`_run_code_job(payload, cancel_check, progress)` 已接收），
task center 里能读到 `phase`。但 `GET /backtests/run-code/{job_id}` **没有把
progress 返回给前端**，前端自然无从展示。

**改动**：
- 后端：状态端点返回 `progress`（取不到时显式返回 `null`，不让进度拖垮状态轮询）
- 后端：`_run_code_job` 为最耗时的 `runner.run(df)` 补一个 `运行策略` 阶段
  （此前该阶段无标记，进度会长时间停在「读取日线」，观感等同卡死）
- 前端：`describeRun()` 渲染「阶段名… 已用时长」，`formatElapsed()` 秒 / mm:ss
- 前端：`pollDelayMs()` 退避轮询（2s 起、×1.5、15s 封顶），
  既保证刚提交有即时反馈，又不为几十秒的任务打上百次请求

实测（真实浏览器 + 真实 API）：

```
✓ 任务已提交，等待调度…
✓ 运行策略… 2s
```

### 7.2 取消运行

**发现**：取消基建同样已存在 —— `request_cancel()` 协作式取消、
`POST /api/tasks/{kind}/{id}/cancel`（kind=backtest 即本队列）都可用，
实测能正确取消 run-code 任务。缺的只是**本页面的入口**。

**改动**：
- 后端：新增 `POST /backtests/run-code/{job_id}/cancel`（404 不存在 / 409 已终态，
  与 ml、qlib 的取消语义一致）
- 前端：运行中右栏显示「取消运行」；409（任务刚好已结束）不当作错误弹给用户

### 7.3 未保存改动保护

**问题**：载入别的策略 / 切 Tab / 新建都会**直接丢弃**编辑器内容，
用户写半天代码点一下左栏就没了。

**改动**：`confirmDiscard()` 纯函数 + 三处接入（新建 / 载入 / 切 Tab）。
`dirty` 为假时不打扰用户。

**过程中被测试抓出的真实缺陷**：初版把初始 `base` 设为 `null`，而
`isDirty(cur, null)` 把「非全空」视为已修改 —— 页面一打开编辑器里就有模板代码，
于是**用户还没动手就会被"未保存修改"拦住**。修法是引入 `NEW_BASE`
（模板 + 默认参数即"新建态的已保存状态"）作为基准。
