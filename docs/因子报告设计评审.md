# 因子报告（HTML tear sheet）设计评审

> 评审时间：2026-10-04
> 评审对象：`src/lquant/factors/evaluate/report.py`（478 行，生成器本体）
> 及其三个入口：CLI `lq factor report`、API `POST /factors/evaluate`、API `POST /factors/synthesize`
> 基线：`main` = `7aa9855`（已含 `b7c1115` 因子分析能力审计修复）

## 一、结论

上一轮审计（`因子分析能力完备性审计.md`）修的是**「能力接不上」**：报告拿不到行业列、拿不到
`group_col`/`bps_list`。这一轮看下来，那些接线问题确实修好了 —— 新生成的报告已经出现
`归因分解 · cov_industry_sw1`、`分组 IC`、`成本敏感性` 三节。

但报告作为**归档物**（要邮件发出、要离线打开、要三个月后回看）的设计仍然不完备，而且缺陷性质
和上一轮是同一类：

| 维度 | 判定 | 依据 |
|---|---|---|
| 能力接线（A1/B1/B2） | ✅ 已修 | 新报告 3 节齐；旧报告是历史遗留（见 R15） |
| **报告身份与溯源** | ❌ **缺失** | 报告不写因子表达式、不写是否中性化、不写数据窗口；244/244 份标题是内部列名（R1–R3） |
| **报告结论** | ❌ **缺失** | 引擎算了 `rating`/`robustness`，报告一个字都没有（R4）；没有摘要区（R5）；没有方案 §5.3 的「IC 归因阶梯」（R6） |
| **静默丢数据** | ❌ **2 处，且有测试固化** | 4 个 `except Exception` 静默删节（R7）；`_table` 静默截断 31 个行业→20 行（R8） |
| **同一报告内口径一致** | ❌ 不一致 | 同一个 `ic_mean`/`positive_rate` 在不同小节一个按 % 一个按原值（R9）；成本表全是裸小数（R10） |
| **同一生成器三个入口一致** | ❌ 不一致 | 衰减期数 8 vs 4、分层组数 10 vs 5、股票池「全部」vs「all」、`window` 被忽略（R12–R13） |
| 报告资产治理 | ❌ 无 | 覆盖写、无版本、旧错误报告仍在被当正常报告列出（R15–R17） |

**一句话**：报告现在**算得全**，但**说不清自己是谁、得出了什么结论、哪些数字被悄悄丢掉了**。
上一轮审计里那句话仍然适用 —— 最危险的是静默，而报告路径上还有两处静默，其中一处还被测试写成了断言。

## 二、缺陷清单（按危害分级）

图例：🔴 静默错误 / 会让人读出错结论 ｜ 🟠 口径不一致 ｜ 🟡 设计缺失 ｜ ⚪ 工程细节

### 🔴 R1. 报告不标识自己是哪个因子（244/244 份）

- **现象**：`data/reports/` 下 244 份 HTML，`<title>` 与 `<h1>` 分别是
  `因子研究报告 · _factor`（242 份）和 `因子研究报告 · _syn`（2 份）。
- **根因**：`factor_report(df, factor, ...)` 的 `factor` 参数**同时承担两个语义** ——
  「DataFrame 里的列名」和「报告的标题」。三个调用方传的都是**内部列名**：
  - CLI：`factor_report(train, "f", ...)`（`cli/commands/factor.py:644`）→ 标题 `f`
  - API 评价：`evaluate(d, "_factor", ...)` → `factor_report(df, "_factor", ...)` → 标题 `_factor`
  - API 合成：`evaluate(d, "_syn", ...)` → 标题 `_syn`（`server/api/factors.py:1442`）
- **后果**：报告脱离调用现场后**无法自证身份**。`data/reports/BETA10.html` 全文 0 次出现
  `BETA10` 这个词；`BETA10_copy.html` 同样。一份被邮件转发的报告，收件人无从知道它评的是哪个因子。
- **讽刺点**：CLI 的 JSON 返回值里**有** `factor` 与 `factor_id`（`factor.py:653-655`），
  但那个信息只进了 stdout，没进 HTML。
- **修复方向**：`factor_report` 增加 `display_name` / `expr` 参数（默认回退到 `factor`），
  三个入口分别传表达式或「已注册因子名」；`<h1>` 与 `<title>` 用 display_name，
  DataFrame 列名不再出现在用户面。

### 🔴 R2. 报告不披露「是否中性化 / 用了什么配方」

- **现象**：报告副标题只有三样东西：`股票池 … · 前瞻收益 … · 生成于 …`（`report.py:408-409`）。
- **缺失**：`evaluate()` 的调用方**明明知道**这些信息却传不进报告：
  - API 侧 `applied_steps`（用户配方）、`cov_map`（协变量覆盖率）、`cat_col` 都在作用域里
    （`server/api/factors.py:597-620`），但 `factor_report` 的签名里**没有** `steps`/`covariates` 参数
    （`report.py:203-213`）。
  - `evaluate()` 的 `_pick` 白名单（`evaluate/__init__.py:108-113`）也不含它们。
- **后果**：这正是方案 §1.1 自己点名的**头号问题** ——「默认中性化是静默假动作」。
  报告是最终交付物，却**回答不了「这份 IC 是原始的还是中性化后的」**。读者无法判断
  「IC 0.03」到底是因子的能力，还是行业/市值暴露的残留。
- **严重性**：上一轮审计修好了「中性化到底吃掉了多少 IC」的计算链路（归因阶梯），
  但**没有修好「把这件事写在报告上」**。报告里既没有中性化前后的对照，也没有一句
  「本报告基于原始因子 / 已按 X 配方处理」。

### 🔴 R3. 报告不写数据窗口与样本量

- **现象**：副标题无日期区间、无样本行数、无交易日数、无股票数、无生成器版本。
- **后果**：与 R1/R15 叠加 —— 一份归档报告**无法回答**「这是哪段时间、多少样本上算出来的」。
  跨期对比两份报告时，读者甚至无法确认它们覆盖的是同一个区间。
- **对比**：CLI 的 JSON 返回了 `n_days`（`factor.py:655`），API 返回了 `n_samples`
  （`factors.py:632`），Web 也展示这些 —— **只有报告这个「最终交付物」不写**。

### 🔴 R4. 报告不含结论：评级与稳健性完全缺席

- **现象**：`report.py` 全文无 `rating` / `robustness` 命中。
- **根因**：`evaluate()` 在**同一个函数体内**先算出评级，紧接着生成报告，却没有把评级传下去：
  ```python
  out["rating"] = factor_rating(...)          # evaluate/__init__.py:99
  ...
  out["report"] = factor_report(df, factor, ...)   # :108 —— 没有 rating 参数
  ```
  `with_robustness=True` 时 `out["robustness"]` 同理，只进了 JSON metrics，没进 HTML。
- **后果**：报告是一堆中间指标（IC、分层、衰减、换手、成本）的堆叠，
  **没有一句「这个因子强不强、稳不稳、差在哪」**。而 `FACTOR_VALIDATION.md:67` 把「评级」
  列为 L2 必测项，`rating.py` 也已经把 IC/ICIR/单调性/多空夏普/多重检验校正收敛成了
  「强/中/弱 + 差在哪」。**结论算出来了，只是没写进交付物。**
- **加重**：用户显式打开 `with_robustness=True`（要重算因子很多遍、很贵）后，
  稳健性结果**依然不在报告里** —— 花了钱，归档物里看不到。

### 🟡 R5. 报告没有「摘要 / 结论」区

- **现象**：报告结构是 `<h1>` → 副标题 → 一串 `<h2>` 小节，**没有任何一段开头的结论**。
- **后果**：读者必须自己把 IC、IR、单调性、半衰期、多空年化、成本表在脑子里合成一个判断。
  报告的自述定位是「能直接邮件发出去」（`report.py:3`）—— 而收件人往往不跑因子模型，
  需要的恰恰是开头那三句话。
- **与 R4 的区别**：R4 是「结论没被算出来/没被传进来」；R5 是「即使算出来了，
  报告也没有承载它的位置」。两者要一起修：R4 供数据，R5 供版面。

### 🟡 R6. 报告缺「IC 归因阶梯」—— 方案 §5.3 定义的「页面核心」

- **方案原文**：§5.3 标题即「**页面核心：IC 归因阶梯**」；§1.1 把「默认中性化是静默假动作」
  列为头号问题。
- **现状**：`neutral_views.py` 的归因阶梯（原始 → 去极值 → 标准化 → 中性化，逐级看 IC 掉了多少）
  在 API 的 `series` 里返回（`neutral_ladder`），Web 主页渲染了，
  **但 `report.py` 完全没有引用** —— 报告里既没有阶梯，也没有中性化前后对照（见 R2）。
- **后果**：整个项目最想回答的那个问题（「中性化到底吃掉了多少 IC」），
  **在归档物里没有答案**。这比 R19 里列的超额/Top-N/风格相关性缺席更严重 ——
  那些是「加分项」，这个是方案自己定义的「核心」。

### 🔴 R7. 报告路径上仍有 4 处静默删节，且被测试固化为「预期行为」

- **现象**：`report.py` 的四个可选节全部 `try/except Exception → None`，异常被完全吞掉：
  | 小节 | 位置 |
  |---|---|
  | 归因分解 | `report.py:256-260` |
  | 分组 IC | `report.py:263-267` |
  | 换手率 | `report.py:269-273` |
  | 成本敏感性 | `report.py:275-280` |
- **后果**：源数据异常 → 整节**无声消失**，读者看到的是「这份报告没有这一节」，
  而真相是「这一节算炸了」。无法区分「不适用」与「故障」。
- **这是上一轮 D1 的同一条缺陷**：审计把 API 的 `except Exception` 改成了回传
  `errors: {块名: 异常}` 并在 Web 渲染错误横幅（`因子分析能力完备性审计.md:63`），
  **但报告生成器内部没改**。API 的 `errors` 字典覆盖不到这里 —— 异常在 `factor_report` 内部就被吃了。
- **更严重的是它被测试锁死了**：
  ```python
  # tests/unit/test_report_gaps.py:186-200
  def test_factor_report_optional_sections_exception_swallowed(monkeypatch):
      ...
      assert "归因分解" not in html      # 断言「炸了就该消失」
      assert "分组 IC" not in html
      assert "换手率" not in html
      assert "成本敏感性" not in html
  ```
  这与上一轮 C5 点名的「桩行为被测试固化」是同一形态：**错误行为被写成断言，改它就会红**。

### 🔴 R8. `_table` 静默截断到 20 行 —— 31 个申万一级行业只显示 20 个

- **根因**：`_table(df, limit=20, ...)`（`report.py:191`），而报告里**所有**表格调用都用默认值
  （`_table(attr[...])`、`_table(gi)`、`_table(cm)`、`_table(prof)`、`_table(yearly)`）。
- **实测**：`data/reports/` 下**归因分解表 244/244 份都恰好 21 个 `<tr>`**（1 表头 + 20 数据行）；
  含「分组 IC」节的 2 份新报告该表同样恰好 21 行。而 `industry_classify` 里申万一级有 **31** 个行业。
  （对照：分层收益表只有 4–6 行 —— 它的行数本来就低于上限，所以没被截断，
  这恰好说明**只有行业维度会撞上 20 这个上限**，而报告里最依赖行业维度的就是这两张表。）
- **两个连带错误**：
  1. **归因分解**：表按 `|exposure|` 降序（`attribution.py:52`），截断丢掉的是 11 个
     |暴露| 最小的行业。但表头上方那行「多空行业暴露总和 …」用的是
     `gross_exposure = exp["exposure"].abs().sum()`（`attribution.py:104`）—— **31 个行业的和**。
     **表格数字与旁边那句话对不上**，且没有任何「已省略 N 行」的提示。
  2. **分组 IC**：`ic_by_group` 返回的是 `df.group_by(group_col)` 的**原始顺序**
     （`group_ic.py:26-42`，无排序），所以截断丢掉的是**任意 11 个行业**，
     而且**每次运行顺序都可能不同** → 报告不可复现。实测新报告里该表顺序是
     银行、社会服务…（既非字典序也非 IC 序），读者无法扫读。
- **修复方向**：`_table` 增加显式 `limit` 语义 + 「仅显示前 N 行（共 M 行）」脚注；
  归因/分组 IC 的行业维度直接不设上限（31 行本来就该全给）；
  `ic_by_group` 输出按 `|ic_mean|` 降序，保证可复现且把最重要的组排在最前。

### 🟠 R9. 同一个指标在报告内被格式化成两种样子

实测自新生成的 `data/reports/BETA10_copy.html`：

| 指标 | 出现位置 | 渲染 | 问题 |
|---|---|---|---|
| `ic_mean` | 分年度 IC 表 | `0.91%` | 按百分比 |
| `ic_mean` | 分组 IC 表 | `-0.0236` | 按原值 |
| `positive_rate` | 分年度 IC 表 | `51.46%` | 按百分比 |
| `positive_rate` | IC 衰减表 | `0.5146` | 按原值 |
| `ic_std` | 分年度 IC 表 | `16.52%` | 按百分比 |
| `ic_std` | IC 衰减表 | `0.1652` | 按原值 |
| `IC 均值` | 核心指标卡片 | `0.0091` | 按原值 |

- **根因**：`pct_cols` 是**逐表手写**的，没有任何全局口径约定
  （`report.py:454` 传了 `("ic_mean","ic_std","positive_rate")`，`report.py:450` 一个都没传）。
- **后果**：同一份报告里 IC 有时是 `0.0091` 有时是 `0.91%`。IC 是相关系数，
  按百分比显示本身就少见；**两种混用**则一定是缺陷。

### 🟠 R10. 成本敏感性表完全没做格式化 —— 而它恰恰是决策表

实测（`BETA10_copy.html`）：

```
bps        gross_annual   net_annual   annual_turnover   viable
0.0000     0.2944         0.2944       41.8791           True
5.0000     0.2944         0.2414       41.8791           True
10.0000    0.2944         0.1905       41.8791           True
```

- `gross_annual` / `net_annual` 是年化收益，却是裸小数 `0.2944`（应为 `29.44%`）——
  同一份报告的分层表里 `annual_return` 就是按 `%` 显示的。
- `annual_turnover` 是倍数 `41.8791`（应为 `41.9x`）—— 上方卡片就是按 `41.9x` 显示的。
- `bps` 显示 `0.0000 / 5.0000 / 30.0000`（应为 `0 / 5 / 30`）。
- `viable` 显示 `True` / `False`（中文报告里应为 是/否 或 ✓/✗）。
- **后果**：这张表的自述是「很多高 IC 因子在这里现出原形」（`report.py:373`），
  是报告里最需要一眼判断的表，却渲染成了最难读的形式。

### 🟠 R11. `_fmt` 把整数类数值一律按 4 位小数渲染

- **根因**：`_fmt` 对任何 `int`/`float` 都走 `f"{v:.{nd}f}"`（`report.py:49`），
  没有「整数值不带小数」的处理。
- **实测**（`BETA10_copy.html`）：`year` → `2026.0000`；`n_days` → `171.0000`；
  分层表的 `q` → `1.0000`；`n_periods` → `171.0000`；`horizon` → `1.0000`；`bps` → `5.0000`。
- **后果**：报告里到处是 `.0000`。同一个 `year` 在柱状图 x 轴上是 `2026`、
  在表里是 `2026.0000` —— **图与表不一致**。

### 🟠 R12. 同一个生成器，三个入口产出三种不同的报告

| 维度 | CLI `lq factor report` | API `/factors/evaluate` | API `/factors/synthesize` |
|---|---|---|---|
| 标题 | `f` | `_factor` | `_syn` |
| 衰减期数 | **8**（默认 `[1,2,3,5,10,20,40,60]`） | **4**（`req.horizons=[1,5,10,20]`） | 4 |
| 分层组数 | **10**（`--n-groups` 默认 10） | **5**（`EvaluateIn.n_groups` 默认 5） | 跟随请求 |
| 股票池显示 | `全部`（不传 universe） | **`all`**（传 `req.universe` 原值） | `全部` |
| 归因分解 | ✅ | ✅ | ❌（不传 `cat_col`） |
| 分组 IC | ✅ | ✅ | ❌（不传 `group_col`） |
| 成本敏感性 | ✅ | ✅ | ❌（不传 `bps_list`） |
| 样本过滤 | ❌（无 `--filter-zscore`） | ✅ | ❌ |

- **证据**：`decay.py:37`（默认 8 期）、`factor.py:638`（CLI `--n-groups` 默认 10）、
  `factors.py:80`（API 默认 5）、`report.py:408`（`universe or "全部"`）。
- **实测**：244 份报告里股票池显示 `全部` 的 242 份、显示 `all` 的 2 份（就是两份新 API 报告）。
- **后果**：这正是上一轮 A1 的原话 ——「**同一平台两种口径**，正是方案最担心的形态」。
  修完 A1 之后，这个形态在**报告内容**层面依然存在，而且现在是三种口径。

### 🟠 R13. 报告的滚动窗口写死 60，用户的 `window` 参数被静默忽略

- **现象**：`report.py:247` `rw = rolling_ic(df, factor, ret_col, 60, ...)`，
  小节标题也写死「滚动窗口（60 交易日）」（`report.py:430`）。
- **而 API 的 `EvaluateIn.window`（默认 60，可设 20–250）只喂给了 series 端点**
  （`factors.py:814`），**没有进 `evaluate()` / `factor_report`**。
- **后果**：用户在 Web 上把 window 调成 120 后，Web 序列图用 120，
  同一次评价生成的 HTML 报告用 60 —— 两个口径，且报告里没有任何提示。
  这与上一轮 B1「`_pick` 白名单漏参数、参数被静默丢弃」是**完全相同的缺陷类型**，
  只是换了个参数。

### 🟡 R15. 报告不可变、无版本 —— 242/244 份仍是修复前的**错误**报告，且被正常列出

- **实测**：`data/reports/` 244 份中，**242 份**的归因小节仍是 `归因分解 · symbol`
  （上一轮 A1 确认的静默错误：按个股算「行业暴露」，却写着「越接近 0 说明中性化越干净」）。
  只有 2 份（`BETA10_copy.html`、`pct_change_20.html`，10-04 生成）是新口径。
  当前代码在隐式路径上**已不可能**再产出 `symbol`（`report.py:254-255` 删掉了回退），
  所以这 242 份只能是修复前的产物 —— 但**报告里没有任何字段能证明这一点**，
  只能靠文件 mtime 猜。
- 同理：**成本敏感性 2/244、分组 IC 2/244、样本过滤 0/244**，
  而事件式 237/244、换手率 237/244（这两节在修复前就存在）。
- **代码已修，工件没修**，而报告里**没有任何版本/生成器标识**（见 R3）：
  读者打开 `BETA10.html` 看到的仍是那个错误结论，**且无从分辨它是修复前还是修复后的**。
- **`/factors/reports` 页面把这 244 份全部平铺列出**（`web/src/app/factors/reports/page.tsx`），
  没有任何「陈旧/已作废」标记，也没有按因子分组。
- **修复方向**：报告写入 `generator_version` / `generated_by`（commit 或版本号）+ 数据区间；
  对口径变更提供失效标记或一键重算；`/factors/reports` 按因子分组并标出生成时间与版本。

### 🟠 R16. 「历史报告」名不副实：是覆盖写，不是历史

- **现象**：`web/src/app/factors/[name]/page.tsx:496` 的面板标题是「历史报告」，
  副标题是 `${data.reports.length} 份`。
- **而 API 每次都写同一个路径**：`REPORT_DIR / f"{req.factor}.html"`
  （`factors.py:627`、`:1447`），**直接覆盖**。所以同名因子的「历史」永远只有 1 份。
- **`BETA10_copy.html` 的存在恰好说明这一点**：用户想要第二份历史，只能手动复制文件
  （`BETA10_copy` 因此还变成了一个**独立的因子名**，见 R17）。
- **修复方向**：要么报告带时间戳/短 hash 保留多份，要么把面板改名为「最新报告」并说明会覆盖。

### 🟠 R17. 「历史报告」用前缀 glob 取文件 —— 会串到别的因子的报告

- **根因**：`factors.py:1362` `REPORT_DIR.glob(f"{name}*.html")`，`name` 后直接跟 `*`，没有分隔符。
- **实测**：`factor_def` 里真实存在的前缀冲突有
  `('BETA10','BETA10_copy')`、`('KLOW','KLOW2')`、`('KMID','KMID2')`、`('KSFT','KSFT2')`、`('KUP','KUP2')`。
  其中 **BETA10 已经实际发生**：`glob("BETA10*.html")` → `['BETA10.html','BETA10_copy.html']`。
  于是**因子 BETA10 的「历史报告」面板里挂着因子 BETA10_copy 的报告**。
  `MA2` → `MA20.html` 的同型问题只要有人建一个叫 `MA2` 的因子就会立刻发生。
- **同一形态**：与上一轮 A1「用错维度顶替」同类 —— 都是「拿了一个看起来像、其实不是的东西」。

### 🟡 R18. CLI `report` 无法做样本过滤，导致「样本过滤」节实际不可达

- **现象**：`lq factor report` 没有 `--filter-zscore`（`factor.py:627-629` 的选项只有
  `--out/--start/--n-groups/--bps`），而 `factor_report` 支持 `filter_zscore`/`outlier_stats`。
- **实测**：**0/244** 份报告含「样本过滤」节。
- **对照**：API 的 `EvaluateIn.filter_zscore` 支持该能力（`factors.py:88`），
  所以这又是一处「能力存在、CLI 门没有」。上一轮 P3 的 D 列表提过
  「CLI `report` 无 `--filter-zscore`」，修复轮没有处理。

### 🟡 R19. 报告覆盖的评价维度仍不完整

引擎有、但报告里**没有**的：超额收益体系（`excess.py`）、Top-N 持仓收缩（`top_n.py`）、
风格相关性体检（`style_corr.py`）、滚动 IR（只画了 RankIC，见 R26）、预处理配方披露（R2）。

其中「IC 归因阶梯」缺席单列在 R6（方案 §5.3 定义为「页面核心」，优先级高于本节其余项）。
本节其余项属**加分项**：报告已经覆盖了 IC/分层/衰减/换手/成本这条主线，
缺的是风格体检与持仓收缩这类「补充证据」。是否纳入属设计取舍，本文只指出缺席。

### 🟡 R20. 报告没有设计契约文档

`docs/lquant因子模块方案（整合版）.md`（283 行）**全文 0 次出现「报告」**。
报告在路线图里被当作 M4 的关键交付物（`ARCHITECTURE.md:404`「M4 结束能在 Jupyter 出因子报告」），
但**没有任何地方规定它必须包含什么**。上面 R1–R19 里有一大半本质是「缺契约」的后果 ——
没有契约，就没法判断一节该不该出现、一个数字该用什么单位、三个入口该不该一致。

### ⚪ R21. 事件式收益图的事件日竖线复刻了 SVG 布局常量

- `report.py:330-331` 为了让竖线对齐事件日，**手写**了 `w, pad_l, pad_r = 640, 46, 10`，
  这三个值必须与 `_svg_multi` 的默认参数（`report.py:126-128`，`pad_l=46, pad_r=10`）**永远保持一致**。
- 一旦有人调整 `_svg_multi` 的默认内边距，事件日虚线会**静默错位**（不报错、只是画歪了）。
- **修复方向**：让 `_svg_multi` 接受一个「按 x 值下标画竖线」的参数（如 `mark_index`），
  由函数内部自己换算坐标。

### ⚪ R22. `REPORT_DIR` 是相对 CWD 的路径

- `factors.py:47` `REPORT_DIR = Path("data/reports")`，CLI 默认输出也是 `Path("data/reports")`
  （`factor.py:650`）。服务进程换个工作目录启动，报告就写到别处；`/factors/reports` 也随之变空。
- 与 `data/` 下其它路径的处理方式不一致（仓库里有 `lquant.core` 的路径解析约定）。

### ⚪ R23. `_table` 无条件丢弃 `nav` 列

- `report.py:194` `cols = [c for c in df.columns if c != "nav"]` —— 为了让分层表不显示净值列。
  但它作用于**所有**表格；任何将来叫 `nav` 的列都会被无声吞掉。应改为调用点显式 `drop_cols`。

### ⚪ R24. 没有打印样式，SVG 缺 `<title>`

- 报告定位是「能直接邮件发出去、能归档」（`report.py:3`），但没有 `@media print` 规则，
  打印/导出 PDF 时卡片与图表的分页、留白不受控。
- 所有内联 SVG 都有 `role="img"` 但**没有 `<title>`/`<desc>`**，屏幕阅读器读不出来。

### ⚪ R25. 「绝不按 symbol 归因」这条不变量只靠调用方自觉

- A1 的修复是**删掉了隐式回退**（`report.py:254-255`），但没有校验 `cat_col` 是不是分类维度。
  `factor_report(df, "f", cat_col="symbol")` 仍会**原样产出**那个被判定为「无意义输出」的
  按个股归因表 —— 而 `tests/unit/test_report_gaps.py:153` **正是这么调的**，
  把它当作正常用法固化了下来。
- 当前三个生产入口都不会传 `symbol`，所以不是活缺陷；但这条不变量应该由
  `factor_report` 自己（或至少由测试）守住，而不是靠调用方。

### 🟠 R26. 滚动小节的文案承诺 3 条线，图里只画了 1 条

- **文案**（`report.py:431`）：「滚动 RankIC / **IC / IR** —— 全样本指标会掩盖阶段性失效」。
- **实际**（`report.py:433-436`）：只画了 `rw["rank_ic_mean"]` 一条线。
- **而数据是齐的**：`rolling_ic` 返回 `date_col, ic_mean, rank_ic_mean, ir, positive_rate, n_days`
  （`rolling.py:55`）—— `ic_mean` 与 `ir` 就在同一个 DataFrame 里，白白没用。
  `_svg_multi` 现成支持多序列（分层净值曲线就在用）。
- **后果**：读者被告知有三条线，实际只有一条 —— 又是「说的和做的不一致」，
  而且这次成本几乎为零（数据已算好，只需换成 `_svg_multi`）。
